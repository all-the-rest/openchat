# ADR 0003 — Internationalization from the First Component

**Status:** accepted (2026-11-17)
**Deciders:** owner

## Context

The product UI must ship English and German, and `AGENTS.md` forbids hard-coded
user-visible strings. The first roadmap draft deferred i18n to M3, which would
have produced a skeleton full of literals that later have to be extracted by
hand — the expensive path.

## Options

1. **Defer i18n to M3.** Fastest first slice, but every component written in M1
   and M2 is retrofitted later.
2. **i18n from the first component.** A small message catalogue and a typed
   translation hook exist before the first screen; every string goes through it.
3. **Full i18n framework with ICU plurals, dates and lazy bundles.** More than
   a single-user prototype needs in M1.

## Decision

Option 2, with Option 3's formatting helpers added only when a screen needs
them.

- Locale bundle: `en` and `de` as flat message maps, one file per locale.
- No runtime dependency on a hosted translation service.
- A typed key union generated from the `en` catalogue; a missing `de` key is a
  build error.
- Locale resolution: explicit user setting → `navigator.language` → `en`.
  The choice is persisted server-side with the owner's settings.
- No user-visible literal in JSX. A lint rule fails the build on text nodes and
  on `aria-label`/`title`/`placeholder`/`alt` literals.
- Tests assert both locales render the same component tree, so a missing key
  cannot pass silently.

## Consequences

- M1 includes the catalogue, the hook and the lint gate.
- Adding a surface means adding keys in both locales in the same change.
- Agents and models keep their own names; do not translate product names.
- The lint gate is a hard CI failure, not a warning.
- Numbers, dates and relative times use `Intl` with the active locale.

## Non-goals

- More than two locales in v1.
- Translating model output.
- Translating documentation.
