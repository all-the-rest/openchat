# 12 — Internationalization

The product UI ships English (`en`) and German (`de`). Rationale and the
decision record: ADR-0003.

## Requirements

- Every user-visible string comes from the message catalogue. No literals in
  JSX text nodes, `aria-label`, `title`, `placeholder`, `alt` or `aria-description`.
- One flat message map per locale; the `en` map is the source of the key union.
- A missing key in either locale fails the build.
- A lint rule fails on hard-coded UI strings. It is a hard CI failure, not a
  warning.
- Locale resolution: stored setting → `navigator.language` → `en`. The setting
  persists server-side with the owner's preferences.
- Switching the language updates the UI without a reload; the page `lang`
  attribute follows the active locale.
- Dates, times, numbers and relative durations use `Intl` with the active
  locale.
- Tests render each component in both locales and assert no raw key leaks into
  the output.

## Non-goals

- Translating model output, agent names or model names.
- Translating documentation.
- More than two locales in v1.
- A translation management service.

## Copy rules

- Write the `en` copy first, then the `de` copy in the same change.
- Keep sentences short; the German string is often 30 % longer, so avoid
  fixed-width labels.
- Do not encode layout in the string (no manual line breaks, no trailing
  spaces).
- Placeholders are named (`{count}`, `{model}`), never positional.

## Acceptance

- `bun run lint` fails when a component contains a literal string.
- A Playwright scenario switches `en` → `de` and asserts a translated heading
  and the `lang` attribute.
- No component file contains a user-visible literal.
