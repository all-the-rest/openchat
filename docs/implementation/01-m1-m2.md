# M1 + M2 — What Runs Today

**Status:** 2026-11-17. Documents the walking skeleton (M1) and the rendering
core (M2) as implemented in `apps/web`, `apps/server` and `packages/opencode`.
It is a map of the code, not a second specification; behavior contracts stay in
`docs/spec/**`.

## Run it

```bash
pnpm install
pnpm run dev            # BFF on :8787, web on :5173
```

Open <http://localhost:5173>, sign in with `OPENCHAT_USER` and
`OPENCHAT_PASSWORD` (or `OPENCHAT_PASSWORD_HASH`), create a chat, send a
message.

Single packages:

```bash
pnpm --filter @openchat/server run start        # BFF only (tsx)
pnpm --filter @openchat/web run dev             # Vite only
pnpm --filter @openchat/opencode run test       # fake backend + fixture
pnpm --filter @openchat/server run test         # auth, sessions, SSE
pnpm --filter @openchat/web run test            # fold, renderers, i18n, composer
pnpm --filter @openchat/web run test:e2e        # Playwright, fake backend
```

All tests run against the fake backend. No test, no dev flow and no E2E needs a
provider, a key or a network call (ADR-0004).

## Processes

```
browser ──HTTP──▶ Vite :5173 ──proxy /api,/healthz──▶ BFF :8787 ──port──▶ ChatBackend
                                                                          ├─ FakeBackend (default)
                                                                          └─ LiveBackend → OpenCode :4096
```

- The browser talks same-origin only; the Vite dev proxy forwards `/api` and
  `/healthz` to the BFF. There is no CORS in the server.
- `apps/server` is a Hono app on Node (`@hono/node-server` is not used; the
  entry uses `node:http` and adapts the request/response to `app.fetch`).
- `packages/opencode` owns the `ChatBackend` port and both adapters. The BFF
  never imports `@opencode/client` directly.

## API

JSON errors are `{ "error": { "code": string, "message": string } }` with 400
(zod), 401, 404 or 500.

| Method | Path | Notes |
| --- | --- | --- |
| GET | `/healthz` | `{ ok, mode, version }`, no auth |
| POST | `/api/auth/login` | `{ password }` → `{ user }` + cookie, or 401 |
| GET | `/api/auth/me` | `{ user }` |
| POST | `/api/auth/logout` | 204 + cleared cookie |
| GET | `/api/info` | `{ server, models, agents, scenario }` |
| GET | `/api/sessions` | `SessionInfo[]` |
| POST | `/api/sessions` | `{ title? }` → `SessionInfo`, directory = `WORKSPACE_DIR` |
| PATCH | `/api/sessions/:id` | `{ title }` → the refreshed `SessionInfo`; 400 invalid title, 404 unknown chat |
| DELETE | `/api/sessions/:id` | `{ ok: true }`; 404 unknown chat (FR-01) |
| GET | `/api/sessions/:id/messages` | `Message[]` |
| GET | `/api/sessions/:id/forms` | `{ forms: FormRequest[] }`; the host's open question forms (FR-16) |
| POST | `/api/sessions/:id/forms/:formID` | `{ answer }` → `{ ok: true }`; the host's answer shape, 404 unknown form, 409 closed form |
| POST | `/api/sessions/:id/prompt` | `{ text, delivery? }` → `{ ok: true, messageID, queued? }`; 30/60 s per address |
| GET | `/api/sessions/:id/inbox` | `{ entries: InboxEntry[] }` |
| DELETE | `/api/sessions/:id/inbox/:messageID` | `{ ok: true }`; unknown session/entry 404 |
| POST | `/api/sessions/:id/interrupt` | `{ ok: true }` |
| POST | `/api/sessions/:id/fork` | `{ messageID }` → new `SessionInfo`; 400 unknown message, 404 unknown session |
| GET | `/api/events` | SSE stream of `EventEnvelope` |

The session cookie is `__Host-oc_session=<user>.<exp>.<hmac>` when `Secure` is
configured (plain `oc_session` in development): HttpOnly, SameSite=Lax, Path=/,
no `Domain`, verified in constant time. Only the active name is read, so a stale
unprefixed cookie cannot authenticate on a Secure deployment. `AUTH_MODE=basic`
compares a Basic header instead, sets no cookie, and shares the login budget.

The cookie is not signed with `SESSION_SECRET` directly. At boot the server
derives a key with HMAC-SHA256 over the configured credential, using
`SESSION_SECRET` as the key: the bcrypt hash in a hash deployment, the plaintext
password otherwise. The HMAC key therefore never equals the secret and the hash
is not exposed, and derivation runs once per boot rather than per request.
Changing the password (the only way today is to replace the hash) changes the
derived key and invalidates every cookie minted against the old one; rotating
`SESSION_SECRET` still invalidates everything. Basic mode sets no cookie, so
revocation there means the next request already carries the new credential.
Logout only clears the browser cookie — there is no server-side session store, so
a copied value stays valid until the TTL or until the credential changes.

Every login attempt is counted against the per-address budget before the
password check, and at most two bcrypt verifications run at once; a burst beyond
that answers `429` with `Retry-After`. A success clears the bucket.

SSE details: `text/event-stream`, `no-cache, no-transform`,
`X-Accel-Buffering: no`, first frame `retry: 2000`, one `data: <json>` frame per
event, heartbeat comment every 15 s, subscriber removed on client abort.

## Edit and branch

`POST /api/sessions/:id/fork` calls `ChatBackend.forkSession(sessionID,
beforeMessageID)`. The live adapter forwards it to `session.fork({ sessionID,
before })`; the fake copies the history before the boundary, leaves the parent
untouched, and inherits the title and instruction entries. Both mark the result
with `branchOf` (parent session) and `branchBefore` (boundary message), never
with `parentID`, so the sidebar's subagent grouping cannot pick a fork up. The
web transcript reads branch counts from the session list, offers **Edit** and
**Branch** on user messages while no run is active, and a branch shows a
"Branch of …" link back to its parent. Editing prefills the composer; sending
forks first and sends the edited text into the new session, so the new history
is the old history before the message plus the edited turn. Cancelling restores
the draft that was in the field.

## Event model

The port normalizes OpenCode events and the fake backend into one envelope:

```ts
{ id, created, type, data, durable? }
```

Types: `session.created`, `session.execution.started`,
`session.execution.succeeded`, `session.execution.failed`,
`session.text.delta`, `session.reasoning.delta`, `session.tool.updated`,
`session.message.completed`, `session.interrupted`, `session.inbox.cancelled`,
`session.usage.updated`, `session.error`.

The web client opens **one** `EventSource` after authentication and folds every
event into the transcript with `applyEvent(messages, event)` (pure function,
unit-tested). Unknown event types return the input unchanged. Deltas append by
`messageID` + `partID` and create the part when it is missing, so a late
subscriber still converges.

## Fake backend scenarios

A prompt prefix selects a scenario for one turn; otherwise `FAKE_SCENARIO`
wins.

| Prefix | What streams |
| --- | --- |
| `rich:` | reasoning deltas, a full Markdown body (h2, bold/italic, inline code, list, GFM table, blockquote, fenced `ts`, inline and block math, fenced `mermaid`), one tool running → success |
| `reasoning:` | reasoning deltas, then a short answer |
| `tools:` | one tool running → success, one tool running → error |
| `error:` | error part, `session.error`, `session.execution.failed`, status `error` |
| `slow:` | long delays (≈400 ms per chunk) for the interrupt test |
| `abort:` | short chunks of a "work in progress" answer, sized so an interrupt lands between deltas |
| `default` | short text answer |

`FakeBackend` is deterministic: injected clock, injected delay (tests use 0),
ids `ses_1`, `msg_2`, `part_3`, … Scenarios emit `message.completed` before
`execution.succeeded`; interrupt stops at the next tick, emits
`session.interrupted` and keeps partial text with status `stopped`.

A prompt sent while a run is active is accepted with `delivery: "queue"`: the
fake appends the user message, answers `{ ok: true, messageID, queued: true }`
and starts the queued turn when the active one ends (success, failure or
interrupt). The BFF defaults to queueing, so a second send never returns a
conflict. `LiveBackend` forwards the mode through `@opencode/client`'s
`session.prompt` and only reports `queued` when `session.inbox.list()` confirms
a pending turn.

## M2 rendering core

All model text goes through one dispatcher (`MessagePart`) with one renderer per
part type. Unknown parts render a neutral fallback, never HTML.

| Part | Renderer | Behavior |
| --- | --- | --- |
| text | `Markdown` | CommonMark + GFM + math + highlighting; raw HTML disabled |
| reasoning | `ReasoningBlock` | expanded while streaming, collapsed after; labelled as reasoning |
| tool | `ToolCard` | name, status, duration, collapsible input/output, truncation with "show full", error state |
| error | `ErrorCard` | message, optional code, retry hint when retryable |
| unknown | fallback | one muted line with the part type |

Markdown safety:

- `rehype-raw` is not installed, so raw HTML in a message is shown as text.
- URLs pass `safeUrl`: only `http(s)`, `mailto`, `#` and `/` survive; `data:` is
  limited to `data:image/`.
- Links render with `target="_blank"` and `rel="noopener noreferrer"`.
- Remote images are not fetched; a payload image must be a data URL, otherwise
  it renders as a link with its alt text.
- Fenced `ts`/`js`/… blocks go through our `CodeBlock` (language label, wrap
  toggle, copy, horizontal scroll, theme-driven highlight tokens).
- Fenced `mermaid` is lazy-imported in an effect, initialized once with
  `securityLevel: "strict"` and a theme matching the app, rendered with a unique
  id; a failure falls back to the source in a `CodeBlock`.
- Inline `$…$` and block `$$…$$` use KaTeX; invalid TeX falls back to text.

Transcript behavior: one scroll container, bottom pinned unless the user
scrolled up (> 64 px), jump-to-latest button when unpinned, no scroll stealing
while streaming, completion announced once through a polite status region.
Under the last assistant message, when no run is streaming, the transcript
offers **Continue** (sends `continue`) and **Retry** (re-sends the last user
message), both keyboard reachable; a queued prompt shows a `Queued` status
until its run starts.

Connection recovery (spec 10 M): the event stream exposes `connection`
(`connecting`/`open`/`closed`) and a `reconnect` counter. While it is `closed`
the chat and landing surfaces show a dismissible `role="alert"` banner
(`chat.connectionLost`); after the counter increments they show
`chat.reconnected` with `role="status"` for five seconds or until dismissed.
The reconnect also reloads the active transcript once and merges the completed
message snapshot by part id, so a backend restart heals without a manual
refresh.

Authentication (spec 10 A): `App.tsx` records the requested route in
`location.state.from`; after a successful sign-in the login page returns there
when it is a same-origin path (starts with `/`, not `//`), otherwise to `/`.

Shell: the mobile sidebar is an off-canvas drawer with `role="dialog"`,
`aria-modal`, `inert` on the content behind it, Escape to close, focus restore
and a Tab trap. Below the `lg` breakpoint the closed drawer is `inert` and its
sidebar is unmounted, so its links stay out of the tab order; on wide viewports
the sidebar remains reachable.

## Bundle split (issue #26)

The initial payload is the login/landing shell. Everything else is a route-level
dynamic import in `apps/web/src/App.tsx` (`ChatPage`, `SearchPage`, `CodePage`,
`AppsPage`, `ArtifactsPage`, `ArtifactViewer`). Each route element sits behind
its own `LazyRoute` boundary, so a navigation keeps the shell mounted and only
the content area shows the centred spinner. `LoginPage` and `LandingPage` stay
eager: they are the first paint, and nothing in them imports the transcript
renderer.

```text
entry (index.html → index-*.js)   App, providers, AppShell, i18n, login, landing
├── ChatPage-*.js                 chat shell, transcript, Markdown, KaTeX glue
│   ├── renderer-highlight-*.js   highlight.js + lowlight  (named Vite group)
│   ├── katex-*.js                KaTeX                     (Rolldown split)
│   └── mermaid.core-*.js → …     lazy Mermaid graph       (dynamic import in Mermaid.tsx)
├── SearchPage-*.js
├── CodePage-*.js
├── AppsPage-*.js
├── ArtifactsPage-*.js
└── ArtifactViewer-*.js
```

`renderer-highlight` is the only configuration on top of the route boundary
(`apps/web/vite.config.ts`, `codeSplitting.groups`): without it the Markdown
chunk lands at ~626 kB because highlight.js' per-language grammars sit in the
same chunk. Splitting the `ChatPage` route itself (header/composer vs
transcript) was tried and left out: it added a second sequential lazy hop and a
second loading state for ~9 kB of chat shell.

| Chunk | Before (raw / gzip) | After (raw / gzip) |
| --- | --- | --- |
| entry `index-*.js` | 1,099.48 / 332.13 kB | 348.53 / 105.02 kB |
| `ChatPage-*.js` | — (inside the entry) | 463.96 / 139.57 kB |
| `renderer-highlight-*.js` | — (inside the entry) | 162.32 / 51.53 kB |
| `katex-*.js` | 258.91 / 77.68 kB | 258.91 / 77.68 kB |
| `SearchPage-*.js` | — (inside the entry) | 8.10 / 2.88 kB |
| `CodePage-*.js` | — (inside the entry) | 6.34 / 2.34 kB |
| `AppsPage-*.js` | — (inside the entry) | 5.54 / 1.74 kB |
| `ArtifactsPage-*.js` | — (inside the entry) | 2.58 / 1.04 kB |
| `ArtifactViewer-*.js` | — (inside the entry) | 14.53 / 4.52 kB |
| Mermaid `elk-*.js` (lazy, exempt) | 1,498.92 / 465.89 kB | 1,498.94 / 465.90 kB |
| Mermaid parser `chunk-*.js` (lazy, exempt) | 629.04 / 127.32 kB | 629.04 / 127.32 kB |

Gate: **no JavaScript chunk above 500 kB, except chunks only the lazily imported
Mermaid graph can reach.** Mermaid exposes two such chunks today (the ELK layout
and the parser core); both are fetched only when a diagram renders, never on
boot. Vite's own 500 kB advisory is raised to 1600 kB in `vite.config.ts`
because the enforced limit is stricter and knows the exemption.

The check is `scripts/check-bundle.ts`, run by `apps/web`'s build script directly
after `vite build`:

```json
"build": "vite build && node ../../scripts/check-bundle.ts"
```

That covers `pnpm run gates:fast` and both CI build jobs without a second build
or a second dependency graph; `deploy/Dockerfile.bff` copies the script into its
build stage for the same reason. A compliant build stays silent; a violation
prints one line per finding and the count on stderr and exits 1. `--list` prints
the machine table (`<bytes>\t<file>\t<reason>`) for humans. It checks four defect
classes:

- a chunk over 500 kB that is not reachable only through `mermaid.core`;
- a route from `LAZY_ROUTES` that is no longer a dynamic import of the entry;
- `LoginPage`/`LandingPage` turned into a dynamic entry;
- the entry chunk itself over the budget (a renderer creeping back into boot).

The split is read from `.vite/manifest.json` (`build.manifest: true`), so the
Mermaid exemption follows the dependency graph rather than a list of chunk
names. A missing `apps/web/dist` exits 2 and says to build first; it is never a
silent pass. This is deliberately not a ratchet rule: the ratchet fast tier runs
in its own CI job with no build and no install, so a dist-reading counter there
would either fail on a clean checkout or force a second build.

i18n: the compiled `en`/`de` catalogues stay in the shared eager chunk
(`icons-*.js`, imported by the entry) and each lazy chunk imports that chunk; the
catalogue is not duplicated into `ChatPage` or any other lazy chunk.

## What is not here (state at 2.5.0)

- **Todos / planning panel.** The pinned client exposes no todo endpoint and the
  event union has no todo event, so the view is not shipped (spec FR-20 allows
  exactly that). An agent's plan renders as a tool card or Markdown list.
- **Image generation (FR-27).** Out of scope by the owner's decision.
- **Citations / source cards (FR-13).** Blocked on the observation that would
  define them; no citation data exists in the wire types today.
- **Attachments as inline previews (FR-12).** Files, images and PDFs render as
  chips with download; the artifact panel previews images and PDFs. An inline
  preview part is blocked on the same observation.
- **Config-only admin proxy (FR-31).** Superseded by the Code surface
  (ADR-0005); the owner retired it there, and no `/admin/opencode` route exists.
- `LiveBackend` is written against `@opencode/client@2.3.0` and typechecks; a
  live smoke test is manual (M7 runbook).
